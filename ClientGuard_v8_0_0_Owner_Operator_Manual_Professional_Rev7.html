Operating model, authorization, and what ClientGuard does#

ClientGuard is a defensive assessment platform for systems and networks you own or are explicitly authorized to assess. It combines network discovery, service detection, conservative vulnerability intelligence, safe validation, evidence handling, and client-ready reporting without turning a correlation into an exploit or an automatic business decision.

1.1 The 10-stage v8 assessment model#

Stage Purpose Operator interpretation
1 Preflight Check runtime, tools, interfaces, storage, and basic readiness. A failed preflight is a reason to stop or repair readiness before scanning.
2 Authorization Bind operator, client, target, scope, and exclusions. The scan must remain inside this boundary.
3 Asset discovery Find reachable authorized systems when discovery is appropriate. A known single /32 target may skip separate host discovery.
4 Service detection Identify reachable ports, protocols, products, and conservative version evidence. Open means exposed, not vulnerable.
5 Vulnerability correlation Compare sufficient product/version/CPE evidence to CVE intelligence. Correlation is not proof.
6 Safe validation Collect additional non-destructive evidence where supported. Validation can increase confidence but does not close or remediate.
7 Evidence processing Preserve observations and receipts. Evidence should remain attributable and reproducible.
8 Risk intelligence Add CVSS, EPSS, KEV, and prioritization context. Risk intelligence assists triage; it does not replace analyst judgment.
9 Reporting Produce HTML/JSON and related artifacts. Read the evidence and confidence, not only the severity label.
10 Governance readiness Support explicit analyst lifecycle actions. READY never means CLOSED.

1.2 Non-negotiable interpretation rules#

  • An open port is exposure evidence, not automatic vulnerability proof.

  • A CVE correlation is a candidate relationship, not exploit confirmation.

  • No CVE match can be the correct result when version/CPE evidence is too generic.

  • Not detected does not mean fixed.

  • Accepted risk does not reduce technical exposure.

  • ClientGuard does not automatically exploit, remediate, close, reopen, accept risk, expand scope, persist credentials, or silently upload/export evidence.

  • Use safe web validation defaults. Do not add destructive SQL injection, file-write, OS-shell, password-attack, persistence, or denial-of-service options to routine assessments.

!

CAUTION: Authorization is a technical input, not a checkbox

Document the client, authorized targets, exclusions, maintenance windows, prohibited actions, and escalation contact before beginning a real engagement. If scope is uncertain, stop and clarify it.

Where ClientGuard runs and what it can assess#

2.1 Operator platform#

ClientGuard v8.0.0 is intended to run from Kali Linux or a compatible Linux assessment workstation where its supporting utilities are available. The target does not need ClientGuard installed. ClientGuard reaches authorized targets over the network and evaluates the services those targets expose.

Normal installed invocation

● ● ●CLIENTGUARD TERMINAL
$ sudo python3 /home/kali/ClientGuard/current/clientguard.py
--assistant

2.2 Target coverage#

Target class Examples What ClientGuard can observe Notes
Windows endpoints Windows 10/11 Pro or Enterprise RPC, SMB, RDP, WinRM, IIS/web services, SQL services, other listening TCP services. Host firewall may intentionally filter services. Version evidence determines whether CVE correlation is possible.
Windows Server Server 2019/2022/2025, member servers, domain controllers AD-related services, DNS, Kerberos, LDAP/LDAPS, SMB, RDP, WinRM, IIS, databases and custom services. Use exact scope and maintenance-window awareness; do not treat exposed AD services as vulnerabilities by themselves.
Linux servers Debian, Ubuntu, RHEL-family, appliances SSH, HTTP/S, DNS, mail, databases, RPC/NFS and application services. Package backports can make banner versions misleading; analyst validation matters.
Web servers / apps Apache, Nginx, IIS, reverse proxies, portals HTTP/S headers, TLS, web fingerprints, Nikto/Nuclei where appropriate, conservative SQLMap checks on explicitly authorized URLs. Web profile is URL-oriented; do not run SQLMap against pages without parameters or authorization.
Routers / firewalls SOHO routers, enterprise gateways, network appliances Management ports, web interfaces, SSH/Telnet exposure, TLS posture and service versions. Router profile is for defensive posture, not credential attacks.
Connected Wi-Fi networks Corporate or lab WLAN after legitimate association Same IP-layer assessment as Ethernet through wlan0. ClientGuard is not a Wi-Fi cracking/deauthentication suite.
BSD / other appliances Reachable networked BSD hosts and service appliances Generic service detection and web/TLS observations. Coverage is service-driven; platform-specific remediation may require analyst context.
Apple/macOS systems MacBook, iMac, Mac mini, Mac Studio, Mac Pro, Apple Silicon or Intel Macs Service-driven network observations such as SSH/Remote Login, SMB, Screen Sharing/VNC, HTTP/S, printing and third-party services when reachable. The target does not need ClientGuard installed. Coverage is network/service driven; local FileVault, Gatekeeper, SIP, MDM and TCC posture require a separate authenticated/local audit.

Apple coverage note: Macs are assessed the same way as other network targets - by authorized reachability and exposed services. Apple Silicon and Intel Macs are both supported as network targets. iPhone/iPad/Apple TV coverage is limited to reachable services and does not constitute a local mobile-device or MDM compliance audit.

2.3 What ClientGuard is not#

  • It is not an EDR agent and does not need to be installed on every target.

  • It is not a credential-dumping, password-cracking, exploit-framework, or persistence tool.

  • It does not prove patch status solely from an open port or generic service banner.

  • It does not replace authenticated configuration auditing when a client requires CIS/STIG policy checks inside the operating system.

Interface, routing, scope, CIDR, and exclusions#

5.1 Identify the interface#

Ethernet and Wi-Fi visibility

● ● ●CLIENTGUARD TERMINAL
$ ip -br addr
lo UNKNOWN 127.0.0.1/8 ::1/128
eth0 UP 10.40.20.44/24
wlan0 DOWN
$ ip route
10.40.20.0/24 dev eth0 proto kernel scope link src 10.40.20.44

Choose the interface whose route actually reaches the authorized target. eth0 is commonly Ethernet; wlan0 is commonly a Wi-Fi adapter. Docker bridges, veth devices, loopback, and unrelated VPN interfaces should not be selected unless the engagement explicitly uses them.

5.2 Scope sizes#

Scope Meaning Typical use
10.40.20.15/32 Exactly one IPv4 host. Safest for a single server, endpoint, router, or appliance.
10.40.20.0/24 Addresses 10.40.20.0 through 10.40.20.255. Authorized subnet assessment; verify exclusions.
scope file A list/ruleset supplied separately. Larger engagements where exact approved ranges are easier to maintain in a file.
--exclude 10.40.20.50/32 Remove a target from an otherwise authorized range. Sensitive equipment, printers, life-safety devices, or client-prohibited hosts.
!

CAUTION: Do not accept the suggested /24 automatically

The assistant may suggest the local subnet. Replace it with the written client scope. A single server engagement should normally use /32, not the entire LAN.

14.7 Large enterprise assessments - 300+ endpoints#

ClientGuard can be used on an authorized environment with hundreds of reachable endpoints, but the professional approach is discover broadly, assess in controlled batches, validate selectively, and preserve the scope for every run. A server does not automatically define the network boundary: the operator must identify the routed subnet(s) and VLANs that are explicitly authorized.

/24256 total addresses; typically 254 usable host addresses.
/23512 total addresses; typically 510 usable host addresses.

CAUTION: Scale does not expand authorization

What to expect with 300+ endpoints

  • Longer run time: filtered ports, slow devices, WAN latency, service probes, and profile depth all increase duration.
  • More network telemetry: firewalls, IDS/IPS, EDR, and SOC tools may generate alerts during an approved assessment. Coordinate the window.
  • Different visibility by VLAN: routing and ACLs determine what the Kali assessment host can reach. One interface does not guarantee visibility into every subnet.
  • Prioritize servers: after inventory, use /32 assessments for high-value systems when you need tighter evidence and easier review.
  • Avoid Deep everywhere by default: use deeper checks selectively rather than turning the broad discovery phase into the most intensive assessment.
  • Preserve exclusions: fragile legacy systems, OT/life-safety devices, or client-prohibited assets should remain explicitly out of scope unless separately approved.
  • Expect incomplete discovery: sleeping devices, host firewalls, endpoint isolation, or NAC can hide systems from a network-based scan.
  • Do not infer remediation: a host or service that disappears on retest is not automatically fixed; investigate and record the analyst disposition.

Enterprise rule of thumb

Use Quick to understand the authorized estate, Standard in manageable subnet/VLAN batches, and Full/Deep or finding-specific validation on selected systems. ClientGuard still does not automatically exploit, remediate, close findings, accept risk, expand scope, or persist credentials.

CHANGED Related condition changed materially; analyst review required.
REGRESSED Previously improved condition has returned/worsened.
NEW Finding appears in retest but not baseline.
NOT_RETESTED No valid retest evidence was collected for that item.
!

CAUTION: Not detected is not fixed

A closed port, timeout, changed firewall, or unavailable service can make evidence disappear. ClientGuard preserves the distinction between absence of detection and verified remediation.

Apple/macOS endpoints, Mac servers, and other Apple devices#

ClientGuard can assess Apple computers from the normal Kali operator workstation without installing ClientGuard on the Mac. The assessment is network/service driven: ClientGuard evaluates what an explicitly authorized Mac exposes over the assessment path, correlates reliable product/version evidence, performs supported safe validation, and produces the same evidence/reporting workflow used for Windows, Linux, routers, and other network targets.

23.2 Common macOS services and what they mean#

A Mac can be quiet on the network or expose several legitimate services depending on System Settings, enterprise management, installed software, and its role. Service presence is not itself a vulnerability. ClientGuard should report reachability and reliable evidence, then correlate only when the product/version information is specific enough.

Port / protocol Common Apple/macOS use Operator interpretation
22/tcp SSH / Remote Login Open means remote shell service is reachable. Review product/version evidence and scope; do not attempt passwords.

5900/tcp Screen Sharing / VNC Reachable remote desktop exposure. Report posture and validation evidence; do not authenticate unless separately authorized.
80/443 tcp Local web service, management UI, development app Use host profile for service posture and Web profile for the exact approved URL when application testing is in scope.
631/tcp IPP / printing May identify printing services. Treat version/CPE evidence conservatively.
548/tcp AFP on older/legacy Mac environments Legacy exposure may justify review, but service presence alone does not prove vulnerability.
3283/tcp Apple Remote Desktop related service in some environments Management exposure may be expected; document reachability and specific evidence.
5353/udp Bonjour / mDNS discovery context UDP discovery is methodology-dependent. A default TCP-focused ClientGuard run may not enumerate this; do not claim absence from a TCP-only scan.

23.7 Apple Silicon versus Intel Macs#

ClientGuard's network-assessment method is the same for Apple Silicon and Intel Macs because the assessment is driven by reachable services and product evidence. Architecture can matter when deciding whether a specific advisory applies, but it must come from reliable evidence or vendor documentation. Do not assign or dismiss a CVE merely because the target is an M-series or Intel Mac.

23.8 What ClientGuard cannot prove from an unauthenticated Mac network scan#

  • FileVault disk-encryption status or recovery-key escrow.

  • Gatekeeper configuration, notarization policy, or local application trust decisions.

  • System Integrity Protection (SIP) state.

  • TCC/privacy permissions, local admin membership, password policy, or secure-token state.

  • MDM enrollment/compliance, configuration profiles, endpoint-security agent health, or local firewall policy beyond externally observed behavior.

  • Complete installed-application inventory or exact macOS patch level when the network service evidence does not expose it.

Those questions require an authenticated/local configuration audit, MDM/EDR evidence, or a separately approved endpoint-assessment method. ClientGuard should not fabricate local compliance from network observations.

23.9 iPhone, iPad, Apple TV, and similar Apple devices#

ClientGuard can only assess services that are actually reachable over the authorized network path. Many mobile Apple devices expose little or nothing to a normal TCP assessment, which may legitimately produce mostly filtered/closed results. Treat that as observed network posture, not proof that the device is fully secure. ClientGuard does not bypass MDM, unlock devices, jailbreak them, extract local data, or perform mobile forensics.
